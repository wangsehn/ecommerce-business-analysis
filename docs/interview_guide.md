# 面试准备指南（interview_guide.md）

> 给求职者的使用说明：**先理解，再背诵**。这里的每个回答都基于你项目里的真实数据和真实代码，
> 你可以用自己的话复述，但务必能追问到底。括号里是"为什么这么答"的点。

---

## A. 项目总览类

### 1. 为什么选择这个数据集？
因为我需要一个能**完整展现数据分析全流程**的真实业务数据：Olist（巴西电商）公开数据集有 9.9 万订单、9.6 万真实用户、8 张关联表，天然具备多表建模、用户/商品/卖家/物流多维分析的素材，且数据量适中——既能体现 SQL 能力，又不会大到让分析失焦。更重要的是它"问题多"：一期付款、重复评价、非交付订单这些坑正好能体现我的口径把控能力。

### 2. 你最重要的发现 / 业务洞察是什么？
一句话：**这是一家"获客驱动而非留存驱动"的平台**。复购率只有 3%，97% 用户只买一单；同时物流超时与评分强相关——超时单均分 2.57 比准时单 4.30 低 1.73 分。这两个发现指向同一条运营主线：与其狂拉新客，不如先做"首单转二单"和"改善履约体验"。

### 3. 项目最大的局限性是什么？
三点：① 我只能得到**相关而非因果**（没有对照实验和混淆变量控制）；② 数据缺用户画像、营销渠道、点击/退款等字段，无法深究"为什么"；③ 时间窗口约 2 年，靠尾部月份的 Cohort 没有后置观察期，早期月份的结论更可信。

## B. 数据建模 / 口径类（高频）

### 4. 为什么用 customer_unique_id 而不是 customer_id？
`customer_id` 是**订单维度**的标识，一个订单一个，用户多次下单会对应多个不同的 `customer_id`；`customer_unique_id` 才是真实用户。用 `customer_id` 数人会把"多次消费的用户"数成"多个人"，用户数、复购率、Cohort、RFM 全都会失真。实测：`customer_id` 去重数 = 订单数 99,441，而 `customer_unique_id` 去重 = 96,096，这个差异直接说明了两个字段语义不同。

### 5. GMV 是怎么定义的？
**有效订单**（delivered）的**商品售价合计**，不含运费。两条理由：① 只有已交付才算成交，cancelled/unavailable 这些没成交的不该算进收入，否则虚增（实测约 2.8%）；② 运费对平台是成本项，平台对商家的 GMV 通常按商品成交价核算，所以我把运费单独列示（约 220 万 BRL）。

### 6. 为什么不能直接 JOIN payment 表统计 GMV？
因为 `order_payments` 是**一单多行**——分期/多次支付时一行一笔。实测约 2,961 单有多次支付，直接 `SUM(payment_value)` 会把这部分订单的金额重复统计，GMV 被夸大。GMV 应从 `order_items` 按商品价算，避免经过支付表。

### 7. 如何避免"多商品订单"导致的重复统计？
一张订单在 `order_items` 里有多行（多商品），如果直接 `COUNT(*)` 计算订单量，会把一单算成多单。所以能做到：计算订单量/客单价的分母用 `COUNT(DISTINCT order_id)`，而 GMV 用 `SUM(price)`（每一行就是一条商品的成交价，天然是订单粒度累加）。

### 8. 客户平均评分你怎么算的？为什么不是直接 AVERAGE(review_score)？
因为一个订单可能有多条评价（实测 547 单同单多评，原始还有 814 行重复 review_id）。直接平均会把"同单多评"这条单放大。我先 `GROUP BY order_id` 取每单平均分，得到"订单均分"，再做二次平均；同时清洗阶段已对 review_id 去重。

## C. 指标体系 / 业务术语类

### 9. 复购率怎么定义？
`复购用户数 / 有购买用户数`，其中复购 = 至少 2 笔不同有效订单，有购买 = 至少 1 笔。算出 3.00%。这是"回头客比例"的语义，用来回答"平台留得住人吗"。

### 10. 客单价（AOV）和复购间隔怎么来的？
AOV = GMV / 有效订单数（137）。复购间隔我用 `LAG` 窗口函数算同一用户**相邻两次**订单的时间差，求平均 79 天、中位数 29 天——注意中位比平均小很多，说明多数复购者约一个月回来一次，平均被少数超长间隔拉高。这和"首末单跨度"是两种口径，我特意选了相邻间隔更符合"回购周期"。

### 11. Cohort 分析怎么做？为什么这么设计？
对每个 `customer_unique_id` 取最早有效购买的月份作为"首购月"，把它按 (首购月, 后置第N月) 聚合出留存用户数，再除以该首购月的总用户数得到留存率%。我特别加了"分母 = cohort 首购人数"这一步——原开源项目只输出留存人数没算率，等于看不出留存好坏。设计上：早期月份有足量后置期更能说明问题。

### 12. RFM 里 R/F/M 各代表什么？你怎么分层的？
R=距最近一次购买天数（越近越高），F=有效购买单数，M=累计 GMV。我用窗口函数跨用户排序，取 30% 分位把每项标记成 高/低，组合成 8 种档位，用于区分"高价值活跃、沉睡高价值、流失边缘"等，指导运营资源投放。这个很容易被追问，我建议你实际跑 SQL 里 `03_customer_analysis.sql` 那份看一眼输出。

### 13. GMV 集中度 / 卖家梯队怎么定义的？
按卖家 GMV 从高到低排序，前 2% 叫头部、2%~20% 腰部、其余长尾——这是"基于分布"的分层而不是拍脑袋定阈值。然后看各梯队 GMV 占比判断平台是否过度依赖头部。

## D. SQL 能力类

### 14. SQL 里用了哪些窗口函数？给了什么业务价值？
用到了：`ROW_NUMBER`（品类内销量冠/中位数求法）、`RANK/DENSE_RANK`（卖家GMV名次且允许并列）、`LAG`（复购相邻间隔、GMV环比）、`SUM/AVG OVER` 配 `PARTITION BY`（GMV 累计占比、各梯队占 GMV、环比）。它们都落在具体业务问题里，比如"环比"不是为了炫"LAG"，而是回答"哪个月份增长异常"。

### 15. 举例说明子查询和 CTE 的区别及在你的使用场景？
CTE（`WITH ... AS`）让长查询可读、可复用，比如我在经营总览里把"有效订单"抽成一个 CTE `valid_orders`，后面月度趋势、地区、品类都复用它，避免一条条重复写 `order_status='delivered'`；子查询更多用在"先算一个聚合再在外层引用"，比如复购间隔里先按订单粒度算 gap 再求中位数。

### 16. 一个 10 万条的项目里，你怎么保证 SQL 结果对不对？
用了三层：① 数据质量 SQL（`01_data_quality.sql`）核验行数、主键唯一、订单状态分布、孤儿引用；② 关键指标用 Python EDA 交叉印证（复购率 SQL 是 3.00%，pandas 也算出 3.00%，能对得上）；③ 对疑似异常（环比突增、超高延迟卖家）单独下钻看明细。

## E. 可视化 / Power BI 类

### 17. 为什么某张图用折线，另一张用柱状，这张又用散点？
月度的 GMV/订单趋势用折线，因为它更适合展示**时间连续性**和拐点；品类/地区排行用柱状（或横向条形），因为它是**离散类别比较**；品类"订单量 vs GMV"用散点+对数轴，因为它要同时看两个数值维度的分布关系（低价高频 vs 高价低频）。原则是：图要回答具体业务问题，不为炫技画图。

### 18. Power BI 的 4 页为什么这样分工？
按"管理层追问"分：Page1 看整体盘子（GMV/订单/客单价/结构）→ Page2 看用户（留不留、谁复购）→ Page3 看供给（靠什么赚钱、有无依赖）→ Page4 看体验（履约是否伤评分）。每页一个主题、顶部 KPI 卡片、下面少而精的图表，避免一页堆满图。

## F. 规模化 / 落地类

### 19. 如果数据量从 10 万变成 1 亿单，你会怎么做？
很多由当前用的技术并不能直接扛住，需要分层：① 存储上把明细表分区/分库分表，或上云数仓（如 BigQuery/Redshift/Doris）；② 计算上尽量把"高成本聚合"做成离线分层表（口径不变、物化），在线查询命中已算好的结果；③ SQL 上注意索引、避免笛卡尔、把大表 JOIN 改成预聚合/增量更新；④ 用户分析这种大 key 口径（customer_unique_id）上要专项优化。核心是**加分层设计**，把"事实表 + 汇总表 + 指标表"体系建好。

### 20. 如果进入真实公司，你还需要哪些数据才能做更可靠的分析？
最需要的是：**成交/退款与财务口径**（毛利、退款、净 GMV）、**营销与渠道数据**（获客成本 CAC、渠道、点击行为）、**用户画像与会员数据**（性别/年龄/高低价偏好/会员等级）、以及**复购归因数据**（促活触达记录）。有了这些才能把"复购率低"从现象变成可行动的归因。

### 21. 这个项目里有没有"看似合理但实际是坑"的口径，你纠正过吗？
有。最典型两个：① 开源框架把"M/M 首末单跨度"叫"复购间隔"，我改成相邻间隔；② 开源框架的留存只输出人数没算率，我补了分母。还有一个：它的差评率分母用的是笛卡尔放大后的行数，口径是错的，我改成订单级去重口径。这些我都写进了 `docs/audit_report.md` 和 `docs/debug_log.md`。这体现了我不光会写，还会核验和纠错。
